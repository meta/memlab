MCP Server for AI Assistants

The @memlab/mcp-server package lets an AI coding assistant investigate JavaScript memory for you. It is an MCP (Model Context Protocol) server: it gives assistants such as Claude Code, Codex, Cursor, Windsurf and opencode about 150 tools built on memlab's heap analysis.

Instead of clicking through the Chrome DevTools Memory panel, you give the assistant a .heapsnapshot file and ask questions in plain language:

Load /tmp/my-app.heapsnapshot, tell me what is growing, and show me the retainer trace for the biggest offender.

The assistant picks the tools, runs them, and explains what it finds.

What You Can Ask​

  • What is this heap made of? How much is your app's data, how much is bundle source, and how much is the JavaScript engine itself.
  • Is anything growing, and is it a leak? Given a series of snapshots taken while an interaction repeats, which objects grow every time, and whether the growth stops or keeps going.
  • Why is this object still in memory? The chain of references that keeps it alive, and which reference to break.
  • Is the number real? Whether memory is held only by DevTools, a browser extension or a development build, rather than by your app.

● Yes. Each open/close of the settings dialog leaks the whole SettingsDialog. The last snapshot
  holds 4 closed instances, one per cycle, and the count rose at every step: 240 detached <div>s and
  about 875 KB of heap per cycle.

  What keeps each dialog alive is its handleThemeChange listener, which is still registered on
  window.eventBus. Its closure captures the dialog as this/dialog:

  @33471 Window / http://localhost:3000 (native)  ← GC root
    .global_object → @33803 Window [JSGlobalObject] / http://localhost:3000 (object)
    .eventBus → @47965 Object (object)
    .listeners → @50799 Array (object)
    [3] → @119723 Object (object)
    .listener → @121371 handleThemeChange (closure)
    .context → @120401 system / Context / scope @65769 (object)
    .this → @120393 SettingsDialog (object)  ← leaked, 787.5 KB

  There is a second reference you have to remove too. The global openedDialogs Set (.table → [i])
  still holds each dialog's Detached <div class="settings">. A scan of every reference into the
  detached DOM found exactly these two app-side holders: that Set and SettingsDialog.container.

  Each dialog still has an unsubscribe closure stored on it, so the close path apparently never
  calls it. The fix: call unsubscribe() on close and openedDialogs.delete(container).

  What a fix saves, measured on the last snapshot:
  - Removing the dialogs frees 3.1 MB (68% of a 4.5 MB heap), about 787 KB per open/close. 99% of
    that is each dialog's history array (781 KB).
  - Clearing the Set frees another ~177 KB of detached DOM (1,992 nodes).
  - Together that's ~3.3 MB, which covers almost all of the 3.5 MB the heap grew.

  Caveats:
  - There is no settle rung (idle + GC), so this can't yet be told apart from in-flight work. A
    dialog that is closed and still on the bus is very unlikely to be that, though.
  - Only 4 cycles were driven.
  - Both roots are page globals (eventBus, openedDialogs). Confirm they're your app's and not a test
    harness's.

Quick Start​

You need Node.js 18 or later. In Claude Code or Codex, install the memlab plugin. It adds the server and Agent Skills that teach the assistant when and how to use it:

# Claude Code
claude plugin marketplace add meta/memlab
claude plugin install memlab@memlab

# Codex
codex plugin marketplace add meta/memlab
codex plugin add memlab@memlab

For other assistants, see Install and Set Up.

Then take a heap snapshot of your page (in Chrome DevTools: Memory → Heap snapshot → Take snapshot → right-click → Save...) and ask the assistant to load it.
